# دليل عرض المتطلب الثالث (الأداء والتخزين المؤقت) — نص المقدّم

> الهدف: أمر واحد يعرض في الطرفية **قبل** و**بعد** كل تحسين بأرقام تُقاس لحظة التشغيل (لا أرقام مكتوبة يدويًا).
> ملاحظة: مخرجات السكربت بالإنجليزية وبحروف ASCII فقط (طرفية ويندوز لا تُشكّل العربية).

## 1) الأوامر

```powershell
# العرض الكامل (حوالي 8 دقائق)
py scripts/demo_req3.py            # أو:  make demo

# العرض السريع (حوالي 3 دقائق أو أقل)
py scripts/demo_req3.py --quick    # أو:  make demo-quick

# أثناء الشرح: يتوقف بعد كل خطوة حتى تضغط Enter
py scripts/demo_req3.py --pause

# خطوة واحدة فقط (مثلًا ETag = الخطوة 6)
py scripts/demo_req3.py --step 6

# زمن الحمل لكل نسخة بالثواني (الافتراضي 20، وفي --quick 10)
py scripts/demo_req3.py --duration 30

# خطة احتياطية: يطبع آخر نتائج محفوظة دون تشغيل شيء (لا يحتاج Docker)
py scripts/demo_req3.py --from-results

# بدون ألوان
py scripts/demo_req3.py --no-color
```

* السكربت يستخدم Python القياسي فقط (بدون مكتبات جديدة)؛ كل شيء ثقيل (docker, k6, mysql) يعمل داخل الحاويات.
* "قبل" = حاوية baseline مبنية بـ `git archive` من آخر commit **قبل** أي تعديل في المتطلب الثالث (منفذ 8010) + الفهارس الأصلية.
  "بعد" = الخدمة النهائية (منفذ 8000). السكربت يبدّل الفهارس والإعدادات تلقائيًا ويُعيد كل شيء في `finally`
  (الفهارس، `SOURCE_DELAY=0`، تشغيل Redis والـ replica والمخزن)، ويحذف بياناته `req3_demo_*`. لا يحذف بيانات seed ولا volumes.
* آخر نتيجة تُحفظ في `loadtest/results/demo_last.json` (تُستخدم مع `--from-results`).

## 3) أسئلة المناقشة المحتملة وأجوبتها القصيرة

**لماذا يختلف p99 عن p50؟**
p50 هو الطلب "العادي" ونصف الطلبات أبطأ منه؛ p99 هو ذيل التوزيع: الطلب البطيء 1 من كل 100. الذيل يتضخم بسبب الانتظار في الطابور (عامل Python واحد)، وملء الـ cache البارد، وجمع القمامة، وطلبات الكتابة. لذلك نعرض الاثنين: المتوسط يخفي الطلبات السيئة.

**لماذا لا نخزّن المخزون (stock) في الـ cache؟**
لأنه أساس ضمان "عدم البيع الزائد" في المتطلب الثاني. لو أظهرنا رقمًا قديمًا لاشترى مستخدم ما نفد. لذلك الـ cache يحتوي الجزء الثابت فقط (الاسم، الوصف، السعر، الفئة) ويُدمج المخزون الحي من المستودع في كل طلب.

**ما هو read-your-writes ولماذا نحتاجه؟**
الـ replica يتأخر قليلًا عن الـ primary. من ينشئ طلبًا ثم يفتح "طلباتي" فورًا قد لا يجد طلبه. بعد كل كتابة ناجحة نضع في Redis علامة `ryw:{user}` لمدة 5 ثوانٍ (أكبر من أقصى تأخر قسناه)، وقراءات هذا المستخدم تذهب للـ primary خلالها. الضمان لصاحب الكتابة فقط، لا لغيره.

**ما الذي يبطّئ الفهرس؟**
الكتابة: كل INSERT/UPDATE/DELETE يحدّث كل فهرس ثانوي، ويستهلك الفهرس مساحة وذاكرة. لذلك حذفنا الفهرسين البسيطين الزائدين (`idx_category_id`, `idx_orders_user_id`) لأن الفهرسين المركّبين يغطيانهما. قياسنا: لا فرق قابل للقياس عند 5 طلبات/ث، والتكلفة موجودة نظريًا وتظهر عند كتابة مكثفة.

**لماذا يوفّر 304 عرض النطاق؟**
لأن الخادم يعيد ترويسات فقط بلا جسم عندما يطابق الـ ETag الذي يرسله العميل في `If-None-Match` المحتوى الحالي. الـ ETag = تجزئة بايتات الجسم نفسها. لا يوفّر عمل الخادم في الـ detail لأن المخزون الحي يُحسب كل مرة.

**لماذا نُبطل الـ cache بعد الـ commit فقط؟**
لو أبطلنا قبل الـ commit لقرأ طلب آخر الصف القديم وأعاد ملء الـ cache به وبقي قديمًا طوال الـ TTL. وإن فشل الـ commit لا يجب أن نُبطل شيئًا لأن شيئًا لم يتغيّر (اختبار: `test_list_uses_a_version_namespace_and_failed_update_does_not_invalidate`).

**لماذا يقرأ ملء الـ cache من الـ primary وليس من الـ replica؟**
بعد الإبطال مباشرة يُعاد الملء. لو قرأ من replica متأخر ثانية أو اثنتين لخزّن الصف القديم تحت المفتاح الجديد وبقي حتى انتهاء الـ TTL، فلا يظهر تعديل المدير رغم أن الإبطال نجح. الـ primary هو المصدر الوحيد الدقيق دائمًا.

**ماذا يحدث إذا توقف Redis؟**
fail-open: خطأ أو مهلة (150 مللي ثانية) تُسجَّل كتحذير ويُخدَم الطلب من قاعدة البيانات (`X-Cache: BYPASS`)، ولا 500 أبدًا. القراءات التي تحتاج علامة RYW تذهب للـ primary لأننا لا نستطيع إثبات حداثة الـ replica. قاطع دائرة لمدة ثانيتين يمنع دفع المهلة في كل طلب.

**وماذا إذا توقف الـ replica؟**
أول قراءة تكتشف أن الاتصال ميت (`pool_pre_ping`)، تُسجَّل تحذيرًا، ويُفتح قاطع دائرة 5 ثوانٍ تُخدَم خلالها كل القراءات من الـ primary. لا 500. يعود تلقائيًا بعد عودة الـ replica.

## 4) قائمة تحقق قبل العرض

1. `docker compose ps` — كل الخدمات `Up/healthy` (بما فيها `db-replica` و`redis`).
2. شغّل `py scripts/demo_req3.py --quick` مرة قبل العرض (تسخين + تأكد أنه PASS).
3. أبقِ `py scripts/demo_req3.py --from-results` جاهزًا كخطة احتياطية.
4. أغلق التطبيقات الثقيلة الأخرى: الجهاز المحمول يتأثر بها (الأرقام تتذبذب بين تشغيل وآخر؛ لذلك نقارن بالتناوب).
